Here's a complete node-by-node spec you can use directly to build this in LangGraph.

---

## Node descriptions

### 1. Employer inputs
This is not an agent — it's the entry point that populates the graph state. The user submits a form (role, tech stack, domain, seniority level). This data gets written into the shared state object and never changes for the rest of the run. Every downstream node reads from it. Keep this as a simple `START` node that validates required fields and rejects if anything critical is missing.

---

### 2. Idea divergence engine
**Type:** Generator LLM call

Prompt it to produce 15 fundamentally different project ideas given the inputs. The prompt must explicitly enforce variety — different system types (realtime, async, event-driven, offline-first), different failure modes, different domains even if the tech stack overlaps. Do not let it produce variations of the same idea with different names. Output: a list of raw idea objects, each with a title and a 2–3 sentence description. Store in `state.ideas`.

---

### 3. Diversity enforcer
**Type:** Filter node (LLM judge or embedding cluster)

Takes `state.ideas` and removes semantic duplicates. The simplest implementation is an LLM call that scores every pair for similarity and drops the lower-scoring one from each similar pair. A better implementation embeds all ideas, clusters them, and picks the centroid of each cluster. Output: a reduced list stored in `state.filtered_ideas`. Aim to keep 5–8 maximally distinct ideas.

---

### 4. Anti-AI filter
**Type:** Critic LLM call + conditional edge

Scores each idea in `state.filtered_ideas` on three axes: (a) can GPT solve this in under 30 minutes, (b) is this a known template or boilerplate problem, (c) is this easily Googleable. Each axis returns 0–3. Ideas scoring below a threshold are rejected. **Conditional edge:** if fewer than 2 ideas survive, route back to node 2 (idea divergence engine) and regenerate. Otherwise pick the top-scoring idea, write it to `state.selected_idea`, and continue. Cap this loop at 3 attempts to prevent infinite cycles.

---

### 5. Constraint injector
**Type:** Mutator LLM call

Takes `state.selected_idea` and enriches it with deliberate friction. Specifically it should add: at least one incomplete requirement (something the candidate has to ask about or decide), one conflicting goal (e.g. "minimize latency" vs "minimize cost"), one scaling edge case, and one failure condition the system must handle gracefully. These constraints intentionally make the problem messier and more ambiguous. Output: `state.constraints` (a list) appended to the idea object. This node is also the re-entry point for Loop 2 — if self-critique fails later, execution comes back here.

---

### 6. Scenario transformer
**Type:** Mutator LLM call

Converts the abstract idea + constraints into a grounded narrative. The transformation is: "Build X" → "You've joined an early-stage company where X is broken. The current system does Y. Your team lead has asked you to fix/build/redesign it by [deadline]." This step is one of the highest-leverage nodes in the whole pipeline. A well-written scenario makes the assignment feel real, raises the perceived difficulty, and naturally hides the "right" answer inside a messy context. Output: `state.scenario` (a multi-paragraph string).

---

### 7. Adversarial agent
**Type:** Critic LLM call

Red-teams the scenario. The prompt gives the agent the role of a lazy but clever candidate and asks: how would you shortcut this using AI? How would you hardcode a solution? What parts of the requirements could you ignore entirely and still produce something that looks complete? What assumptions could you exploit? Output: `state.vulnerabilities` — a structured list of specific weaknesses, each with a short description of the exploit.

---

### 8. Patch node
**Type:** Mutator LLM call

Takes `state.vulnerabilities` and mutates the scenario and constraints to close each gap. For each vulnerability, it either adds an observable requirement that a hardcoded solution cannot satisfy, introduces dynamic inputs that break template solutions, or adds an evaluation signal that catches lazy AI-generated answers. Output: overwrites `state.scenario` and `state.constraints` with the patched versions.

---

### 9. Evaluation designer
**Type:** Designer LLM call

Produces the scoring rubric tied to the patched assignment. It must output structured scoring dimensions — each dimension has a name, a weight, a description of what excellent looks like (4–5), what passing looks like (2–3), and what failure looks like (0–1). Recommended dimensions: handles ambiguity, tradeoff articulation, edge case coverage, system design clarity, communication quality. Output: `state.evaluation_rubric` as a structured object.

---

### 10. Self-critique loop
**Type:** Meta-critic LLM call + conditional edge

Reviews the full state — scenario, constraints, rubric — and answers three questions: is this still solvable via a template? Does it actually test thinking or just implementation speed? Is the rubric specific enough to differentiate strong from weak candidates? Returns a pass/fail verdict plus a list of specific issues. **Conditional edge:** if issues are found AND `state.critique_iterations < 3`, increment the counter and route back to node 5 (constraint injector) for another refinement pass. If it passes (or max iterations reached), continue to node 11.

---

### 11. PRD generator
**Type:** Formatter LLM call

Assembles everything in `state` into the final structured document. It has two output sections — candidate-facing and interviewer-only. The candidate-facing section includes: context and narrative, problem statement, constraints (intentionally incomplete), requirements, and deliverables. The interviewer-only section includes: evaluation rubric, scoring signals, hidden traps, and what a strong vs weak submission looks like. Output: `state.final_prd` as a formatted string or structured JSON ready to render.

---

## State object

```python
{
  "employer_input": {},        # role, stack, domain, seniority
  "ideas": [],                 # raw ideas from node 2
  "filtered_ideas": [],        # after diversity enforcement
  "selected_idea": {},         # top scorer after anti-AI filter
  "idea_loop_count": 0,        # cap loop 1 at 3
  "constraints": [],           # injected by node 5, patched by node 8
  "scenario": "",              # built in node 6, patched in node 8
  "vulnerabilities": [],       # from adversarial agent
  "evaluation_rubric": {},     # from node 9
  "critique_iterations": 0,    # cap loop 2 at 3
  "final_prd": ""              # assembled by node 11
}
```

## The two loops to implement

**Loop 1** — between nodes 4 and 2. Triggered when the anti-AI filter rejects too many ideas. Hard cap at 3 iterations. If still failing after 3 rounds, surface an error state rather than looping forever.

**Loop 2** — between nodes 10 and 5. Triggered when self-critique finds real issues with the assignment. Hard cap at 3 iterations. After 3 rounds, pass regardless so the pipeline always terminates.
